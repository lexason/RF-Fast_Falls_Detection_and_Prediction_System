### 2026-07-17 — Firmware reflash attempted, root-caused as an upstream build inconsistency (BLOCKED, ≥2 attempts)
Did: Researcher approved the reflash. Ran `uhd_image_loader --args="type=usrp2,addr=192.168.10.50"`; it correctly identified the device as "USRP N210 r4" and flashed `usrp_n210_fw.bin` + `usrp_n210_r4_fpga.bin` — both reported "successful" (erase/write/verify all passed). Rebooted device, reran `uhd_usrp_probe`: **identical failure**, still "Expected FPGA compatibility number 11, but got 10."

Investigated rather than reflashing blindly a third time:
- Downloaded fresh images from files.ettus.com (network reachable) to a scratch dir instead of the system images path (no write access there, sudo needs a password I don't have) — the freshly-downloaded `usrp_n210_r4_fpga.bin` is byte-identical (md5 `e691860c6c6a1f5e07b1d466d673095a`) to the one already flashed. Re-flashing would reproduce the exact same result.
- Found the UHD source tree at `~/src/uhd`, checked out at tag `v4.9.0.0` (commit `006d7f764`) — this is what `/usr/local/bin/uhd_usrp_probe` was built from (matches the `UHD_4.9.0.HEAD-0-g006d7f76` version string; no apt-packaged UHD binaries exist to fall back to).
- Root cause, in `host/lib/usrp/usrp2/fw_common.h`: `USRP2_FPGA_COMPAT_NUM=10` (legacy USRP2 rev3/4) vs `N200_FPGA_COMPAT_NUM=11` (N200/N210 family). `usrp2_impl.cpp` correctly identifies this device as `USRP_N210_R4` and therefore requires compat **11**.
- But `images/manifest.txt`, pinned in this same `v4.9.0.0` tag, points the *only* available N210 FPGA target (`usrp2_n210_fpga_default`) at build `fpga-6bea23d`, which is compat **10**. There is no other N210 entry in the manifest. This is an internal inconsistency in the v4.9.0.0 release artifacts themselves — the host code's compat requirement for N210 and the pinned FPGA image build disagree, and no image satisfying compat 11 is reachable through the normal download path.

Learned: This cannot be fixed by reflashing again — confirmed the "correct" image per UHD's own manifest is exactly what's already on the device. Genuinely blocked.

Alternatives proposed to researcher (see next entry for decision):
1. Build a compat-11 N210 FPGA bitstream from the HDL sources in `~/src/uhd/fpga/` using Xilinx tools — correct long-term fix but needs a Xilinx toolchain/license and real synthesis time; unknown if available on this machine.
2. Build and use an older/stable UHD release (e.g. an actual 4.6.x tag) in a separate prefix, whose N210 host-code compat expectation matches the already-available compat-10 image — fastest path to unblock G0, but means not running v4.9.0.0 for USRP2-family hardware; would need a decision-log entry since it changes the software stack.
3. Check for a newer upstream commit past `v4.9.0.0` that corrects the manifest pin or the compat requirement (`git fetch` + rebuild) — plausible if this is a known, already-fixed upstream bug, but adds rebuild time and no guarantee a fix exists yet.
4. (not recommended) Patch `N200_FPGA_COMPAT_NUM` down to 10 locally and rebuild, to force-match the available image — bypasses a real protocol/register-map compatibility guard UHD added deliberately; risk of undefined behavior talking to real RF hardware. Flagged but deprioritized.

Next: Awaiting researcher decision among the above before touching firmware or the UHD build again.
